## 1. 씬 선별 — bbox가 아니라 footprint로

### 1-1. 왜 footprint인가

Sentinel-1 IW 프레임은 궤도 방위각만큼 기울어진 **평행사변형**이다. 이것을
경위도 축에 정렬된 bbox로 감싸면 **실제로 찍지 않은 삼각형 여백**까지
"촬영 지역"에 들어간다. 그 여백이 한반도에 걸치면 **100% 바다인 프레임이
"한반도를 찍었다"로 오판**된다. 이 오판이 실제로 침수 수치를 아티팩트로
만든 사고가 있었다([SCENE_FOOTPRINT_REAUDIT_KR.md](SCENE_FOOTPRINT_REAUDIT_KR.md)).

### 1-2. 판정 방법

원본 zip 안의 `preview/map-overlay.kml`에서 실제 촬영 폴리곤을 읽어,
`geojson/South_Korea.geojson`과 point-in-polygon으로 대조한다.

1. footprint 폴리곤의 bbox에 **0.01° 격자점**을 뿌린다.
2. 격자점 중 footprint 내부인 것만 남긴다(ray-casting).
3. 그중 남한 경계 내부 비율 = **남한 커버율(%)**.

로직은 [footprint/footprint_aoi.py](../../s1/footprint/footprint_aoi.py)에 모여 있다
(shapely 계층 / 순수 numpy 계층 2종 —
[footprint/FOOTPRINT_AOI_KR.md](FOOTPRINT_AOI_KR.md)).

### 1-3. 선별 결과

- **2026-07**: 20개 궤도그룹 중 남한이 걸리는 **11개**. 남한 0%인 9개 궤도
  (07/03 o008377, 07/04, 07/06, 07/07, 07/16 ×2, 07/18, 07/19, 07/28)는
  RTC는 이미 있어도 수체 판별 대상에서 제외.
  7/27 미처리 4씬 중에서도 남한 0%인 DF80·32ED는 **RTC 자체를 돌리지 않았다.**
- **2025-07**: 로컬 GRD 16씬 **전부** 남한이 걸림(1.8% ~ 84.4%). 제외 없음.

## 2. 전처리 — GRD → RTC(Gamma0) dB GeoTIFF

SNAP `gpt`를 snapista로 구동한다. 그래프 정의는
[prepro_grd_gpt.py](../../s1/preprocess/prepro_grd_gpt.py)의 `build_grd_rtc_graph`.

### 2-1. 처리 체인

```text
Read
 → Apply-Orbit-File          정밀궤도 적용 (Sentinel Precise, Auto Download)
 → ThermalNoiseRemoval       열잡음 제거
 → Calibration (Beta0)       Terrain-Flattening 입력 요건
 → Speckle-Filter (Frost)    스페클 억제
 → Terrain-Flattening        지형 경사·향에 의한 밝기 왜곡 정규화 = RTC의 핵심
 → Terrain-Correction        지오코딩 (10 m, EPSG:4326)
 → LinearToFromdB            선형 → dB
 → Write                     <씬ID>_rtc_db.tif (GeoTIFF-BigTIFF)
```

각 단계의 **이유**:

- **Apply-Orbit-File** — 헤더의 예측궤도는 수십 m 오차가 있다. 정밀궤도로
  갈아끼워야 지오코딩 위치가 맞는다. `continueOnFail=false`로 두어 궤도를
  못 받으면 조용히 틀린 결과를 내는 대신 실패하게 한다.
- **ThermalNoiseRemoval** — 저후방산란 영역(=물)에서 열잡음 비중이 크다.
  수체 판별은 어두운 쪽 꼬리를 보는 작업이라 이걸 안 빼면 물 봉우리가
  잡음에 묻힌다.
- **Calibration → Beta0** — Terrain-Flattening의 입력은 Beta0여야 한다.
  (대조군 GTC는 여기서 Sigma0를 내고 Terrain-Flattening을 건너뛴다.)
- **Speckle-Filter (Frost)** — 2026-07-23에 Refined Lee(7×7)에서 Frost
  (SNAP 기본 3×3, damping 2.0)로 바꿨다. 스페클 억제는 동등하면서 **가는
  수로·경계 보존이 우수**하기 때문([FILTER_COMPARISON_KR.md](FILTER_COMPARISON_KR.md) §2·§6).
  **25·26년 양쪽을 모두 Frost로 처리했다** — dB 절대값이 필터에 따라 달라져
  임계값 비교가 어긋나기 때문에 이 통일이 연도 간 비교의 전제다.
- **Terrain-Flattening** — DEM 국지 입사각으로 경사면 밝기를 정규화한다.
  이게 없으면 산지 사면이 어둡게 남아 물로 오판된다. 씬당 처리시간의
  60~70%를 차지한다.
- **Terrain-Correction** — Range-Doppler 지오코딩. 10 m 픽셀, EPSG:4326.
- **LinearToFromdB** — 이후 임계값을 dB로 다루기 위해.

### 2-2. 파라미터

| 항목 | 값 |
| --- | --- |
| 편파 | VV |
| 궤도 | Sentinel Precise (Auto Download), polyDegree 3, continueOnFail false |
| 열잡음 | removeThermalNoise=true |
| 캘리브레이션 | Beta0만 출력 (Sigma0·Gamma0 off) |
| Speckle 필터 | Frost (SNAP 기본 3×3, damping 2.0) |
| DEM | Copernicus 30m Global DEM (자동 다운로드) |
| DEM 리샘플링 | BILINEAR_INTERPOLATION |
| 영상 리샘플링 | BILINEAR_INTERPOLATION |
| 픽셀 간격 | 10 m |
| 좌표계 | EPSG:4326 |
| 출력 | dB, GeoTIFF-BigTIFF |
| gpt 옵션 | `-q 8 -c 14G` (기본) |

### 2-3. 배치 실행

[batch_grd_rtc_frost.py](../../s1/tools/preprocess/batch_grd_rtc_frost.py)가 러너다.

```bash
# 26년 7월 전체
conda run -n s1_snappy python batch_grd_rtc_frost.py --month 202607

# 특정 씬만 (남한 footprint 씬만 골라 돌릴 때)
conda run -n s1_snappy python batch_grd_rtc_frost.py --month 202607 --only 08EE,9B8B

# 25년 7월
conda run -n s1_snappy python batch_grd_rtc_frost.py --month 202507 --oldest-first
```

러너가 하는 일:

- `--month` 접두사로 대상 zip 선별, 기본 **최신 날짜 먼저**(`--oldest-first`로 반대).
- 입력 zip을 **C: SSD의 씬별 임시 폴더로 복사**한 뒤 처리한다. HDD/네트워크
  랜덤 읽기가 병목이라 복사가 오히려 빠르다. 폴더로 격리해 원본 파일명을
  유지하므로 산출물 이름이 `<씬ID>_rtc_db.tif`로 깔끔하고, 동시 실행해도
  충돌하지 않는다. 처리 후 임시 폴더 삭제.
- **이미 산출물이 있으면 건너뛴다** — 중간에 끊겨도 이어서 재실행 가능.
- 실패 시 반쯤 쓰인 tif를 지우고 다음 씬으로 넘어간다.
- `--gpt-q` / `--gpt-c`로 자원 조절. 실측상 gpt는 `-q 8`을 줘도 1코어 남짓만
  쓰고 디스크도 유휴라, **배치 2개를 병렬로 띄우는 편이 총 처리시간이 짧다.**
  그때는 캐시를 `--gpt-c 6G`~`7G`씩 나눠야 RAM 32GB를 넘기지 않는다.

**실측 처리시간**: 씬당 15~80분(프레임 크기·중첩에 따라). 26년 7/27
08EE는 15분, 9B8B는 30분이었고, 큰 프레임은 70분대도 나온다.

## 3. 궤도 그룹핑과 VRT 모자이크

### 3-1. 왜 궤도별로 묶는가

같은 날짜라도 **절대궤도번호가 다르면 다른 패스**다. 궤도가 다르면
입사각·촬영기하가 달라 후방산란 dB 분포 자체가 다르다. 여러 궤도를 한
히스토그램에 섞으면 임계값이 왜곡되므로, **(날짜, 절대궤도)를 키로 묶어**
그룹마다 따로 모자이크 → 따로 Otsu → 따로 판정한다.

파일명에서 뽑는다:
`S1C_IW_GRDH_1SDV_<날짜>T<시각>_..._<절대궤도>_<takeID>_<씬ID>_COG_rtc_db.tif`

### 3-2. VRT

그룹마다 `gdalbuildvrt`로 가상 모자이크를 만든다:

```bash
gdalbuildvrt -srcnodata 0 -vrtnodata 0 -overwrite \
    downloads/water_otsu/vrt/mosaic_<날짜>_o<궤도>.vrt <프레임들의 절대경로>
```

- **실제 픽셀을 합친 GeoTIFF가 아니다.** 2~5 KB짜리 XML 참조 파일이라
  8프레임 궤도(수십 GB)도 메모리 부담 없이 다룰 수 있다. 이후 처리는
  이 VRT를 청크 단위로 훑는다.
- `-srcnodata 0 -vrtnodata 0` — 프레임 가장자리의 0값을 미관측으로 처리해
  겹침 구간이 히스토그램을 오염시키지 않게 한다.
- 소스를 **절대경로**로 넣어 VRT를 옮겨도 열린다. QGIS에서 이 VRT를 바로
  띄워 궤도별 dB 모자이크를 눈으로 확인할 수 있다.

## 4. 수체 판별 — 타일 기반(split-based) Otsu

구현: [build_water_per_date_otsu.py](../../s1/tools/water/build_water_per_date_otsu.py).
이론적 배경과 레퍼런스(Martinis 2009, Chini 2017)는
[OTSU_SPLIT_BASED_KR.md](../water/OTSU_SPLIT_BASED_KR.md).

### 4-1. 전역 Otsu를 쓰면 안 되는 이유

물은 VV dB 히스토그램에서 어두운 봉우리지만, 넓은 장면에서 **물 화소는
육지보다 압도적으로 적다**(이 프로젝트 7/3 장면 기준 약 1:150). 전역 Otsu는
클래스 간 분산을 최대화하려고 **다수인 육지 분포를 반으로 가르는 지점
(≈ −8 dB)** 을 고르고, 장면의 절반을 물로 오판한다. 실제로 −8.3 dB,
26,000 km²라는 명백한 오탐이 나왔다.

### 4-2. 알고리즘

1. **타일 분할** — 궤도 VRT를 1024 px(≈10 km) 타일로 나눈다.
2. **타일별 Otsu** — 각 타일에서 임계값과 **분리도 η = σ²_B / σ²_T**
   (0~1, 클수록 뚜렷한 이봉), 어두운 클래스 비율을 구한다.
3. **이봉 타일 채택** — 유효 화소 25% 이상인 타일 중, η가 **상위 5%**
   (백분위 95)이고 어두운 클래스 비율이 2~98%인 타일만 고른다.
   물+육지가 함께 있어 진짜 이봉인 타일만 남기는 단계다.
4. **히스토그램 pooling** — 고른 타일들의 히스토그램을 합쳐 **한 번의 Otsu**로
   궤도 전체 임계값을 낸다. 이봉 타일 안에서는 물:육지 비율이 비슷해
   Otsu가 진짜 골짜기(−13 ~ −15 dB)를 찾는다.
5. **적용** — 그 임계값을 궤도 전체에 적용해 0/1/255 래스터를 쓴다.
6. **fallback** — 채택 타일이 8개 미만이면 이봉 근거 부족으로 판단해
   고정 −16 dB로 물러난다(경고 표시). 임계값이 −25 ~ −10 dB 범위를
   벗어나도 경고한다.

### 4-3. 파라미터

| 항목 | 값 | 의미 |
| --- | --- | --- |
| 히스토그램 범위 | −35 ~ +10 dB, 450 bin | 0.1 dB 폭 |
| 타일 크기 | 1024 px | 10 m 해상도에서 약 10 km |
| 유효 화소 하한 | 25% | 이 미만인 타일은 후보에서 제외 |
| 분리도 백분위 | 95 (상위 5%) | 이봉 타일 채택 기준 |
| 어두운 클래스 비율 허용 | 2 ~ 98% | 한쪽으로 치우친 타일 배제 |
| 최소 채택 타일 | 8 | 미만이면 fallback |
| fallback 임계값 | −16 dB | 고정값 |
| 정상 임계값 범위 | −25 ~ −10 dB | 벗어나면 경고 |
| 청크 | 512행 | 메모리 안전 |

### 4-4. 실행

```bash
# 26년 7월 남한 궤도
conda run -n s1_snappy python build_water_per_date_otsu.py \
    --source-dir downloads/rtc_grd_frost --suffix rtc_db --out-suffix _frost \
    --dates 2026 \
    --orbits "003493,003668,003675,003843,008355,008384,008530,008552,008632,008705,008734"

# 25년 7월 남한 궤도
conda run -n s1_snappy python build_water_per_date_otsu.py \
    --source-dir downloads/rtc_grd_frost --suffix rtc_db --out-suffix _frost \
    --dates 202507 \
    --orbits "059976,060049,003280,060151,060224,003375,060326"
```

- `--dates`는 **접두사 일치**(`2026` / `202607` / `20260703`). 25·26년 RTC가
  같은 입력 폴더에 쌓이므로 연도 고정 장치로 쓴다.
- `--orbits`는 절대궤도 화이트리스트. **PowerShell에서는 반드시 따옴표로
  묶을 것**(7-4절).
- 기존 출력이 있으면 건너뛴다. 다시 계산하려면 `--overwrite`.

### 4-5. 산출물

```text
downloads/water_otsu/
  flood_water_total_<날짜>_o<절대궤도>_frost.tif   0=비수체, 1=수체, 255=미관측
  otsu_thresholds.csv                              그룹별 임계값·면적 로그
  vrt/mosaic_<날짜>_o<절대궤도>.vrt                궤도별 dB 모자이크(QGIS 확인용)
```

`_frost` 접미사로 예전 Refined Lee 산출물과 분리했다. 파일명에 관측일이
들어가므로 25·26년이 같은 폴더에 있어도 덮어쓰지 않는다.

## 5. 면적 산정

[water_area_report.py](../../s1/tools/water/water_area_report.py)가 수체(=1) 화소를 세어 면적을 낸다.
EPSG:4326에서 경도 1° 길이가 `cos(위도)`로 줄기 때문에 보정이 필요하다.

- `pixel_centerlat` — 장면 중심위도 하나로 근사(Otsu 스크립트가 로그에 쓰는 값).
- **`pixel_perrow`** — **행(위도)마다** 보정. 폴리곤 측지 면적과 소수점까지
  일치함을 검증했다. 채택값.

두 방식 차이는 대체로 ±1% 이내.

```bash
conda run -n s1_snappy python water_area_report.py \
    --csv downloads/water_otsu/water_area_perrow.csv
```

> **이 면적은 "상태 면적"이지 "침수 면적"이 아니다.** 그 시점에 dB가 물처럼
> 어두운 **전체** 화소(서해·남해·큰 강·저수지 포함)다. 신규 침수량은
> baseline 비교 산출물을 써야 한다([FLOOD_DETECTION_KR.md](../flood/FLOOD_DETECTION_KR.md)).
> 가뭄 지표로 쓰려면 해상을 뺀 내수면 마스크가 선행돼야 한다.

## 7. 겪은 문제와 대응

### 7-1. bbox 오판 (해결)

bbox로 "한반도를 찍었다"고 판정한 프레임이 실제로는 전부 바다였다.
→ footprint 기반 판정으로 전환(1절), 일본/중국 전용 씬은 별도 폴더로 분리.

### 7-2. 전역 Otsu 과대추정 (해결)

−8.3 dB 임계값, 장면 절반이 물. → 타일 기반 split Otsu 도입(4-1절).

### 7-3. speckle 필터 혼재 (해결)

기존 산출물 65개는 Refined Lee, 신규는 Frost. dB 절대값이 달라 고정 임계값
비교가 깨진다. → 26년 7월 전량 + 25년 7월 전량을 **Frost로 재처리**해 통일.
6월 이전(6/25·6/26 12씬)은 원본 zip이 이미 삭제돼 미해결로 남아 있다.

### 7-4. PowerShell이 궤도번호의 앞 0을 떨굼 (해결)

`--orbits 008632,...`를 따옴표 없이 넘기면 PowerShell이 숫자 배열로 해석해
`8632`로 전달한다. 6자리 매칭이 전부 실패해 "처리할 그룹이 없습니다"로
즉시 종료했다. → 인자를 따옴표로 묶고, 스크립트에서도 `zfill(6)`으로 정규화.

### 7-5. 25·26년 입력 폴더 혼재 (해결)

두 해의 RTC가 같은 `downloads/rtc_grd_frost/`에 쌓인다. 필터 없이 돌리면
연도가 섞인다. → `--dates`를 접두사 일치로 바꿔 `--dates 2026` / `202507`로
연도를 고정. 산출물 파일명에 관측일이 들어가 덮어쓰기도 없다.

### 7-6. 프레임 누락 (해결)

25년 7/25 궤도가 4프레임인데 3프레임으로 계산돼 있었다(47FE 누락).
→ 47FE를 RTC 처리한 뒤 그 궤도만 `--overwrite`로 재계산
(−14.85 → −14.75 dB, 957.00 → 1,085.67 km²).

### 7-7. 젖은 토양에 의한 과대추정 (미해결)

26년 7/14 두 궤도는 임계값이 −11.45 / −11.85 dB로 다른 날보다 2~3 dB 높고
η도 0.51/0.57로 낮다. 면적이 Refined Lee 대비 +39% / +17%로 뛰었다.
태풍 직후 젖은 토양이 넓게 어두워지며 이봉 구조가 무너진 것으로 보인다.
→ **검증 전 사용 금지**로 표시. 25년 7/19 fallback 궤도도 같은 취급.

### 7-8. 연도 간 관측 범위 차이 (미해결)

유일한 상대궤도 짝(2025-07-18 o003280 ↔ 2026 계열 A)조차 유효화소가
8.79억 vs 17.85억으로 **2배 차이**난다(프레임 2개 vs 5개). 면적을 그대로
견주면 "26년에 물이 늘었다"는 틀린 결론이 나온다.
→ 공통 관측영역 마스크가 다음 과제([DROUGHT_KR.md](../drought/DROUGHT_KR.md) 3절).
