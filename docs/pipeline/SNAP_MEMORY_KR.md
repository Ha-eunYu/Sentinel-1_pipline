# SNAP gpt 메모리 — `-c`는 상한이 아니다

2026-08-03에 SNAP `gpt` 4~5개를 같이 돌리다 한 건이 죽고 한 건이 무한정 헛돌았다.
원인은 **`-c` 옵션을 프로세스 메모리 상한으로 착각한 것**이다. 같은 실수를 막기
위해 구조와 진단법을 정리한다.

---

## 1. 세 줄 요약

| | |
|---|---|
| **무엇을 착각했나** | `-c 8G`를 "이 프로세스는 8 GB만 쓴다"로 읽었다 |
| **실제** | `-c`는 **타일 캐시**일 뿐이고, 힙 상한은 `gpt.vmoptions`의 **`-Xmx22G`** 다 |
| **결과** | 31.7 GB 장비에서 4건 동시 실행 → 페이징 → GC 스래싱 → 1건 사망, 1건 정지 |

## 3. SNAP gpt의 메모리 구조

`gpt.exe`는 JVM 런처다. 프로세스가 쓰는 메모리는 세 덩어리다.

```
  ┌─ JVM 힙 ──────────────────────────────┐
  │  상한 = gpt.vmoptions 의 -Xmx         │  ← 이 장비는 22G
  │  ┌─ 타일 캐시 ─────────┐              │
  │  │  상한 = -c 옵션      │              │  ← 8G / 5G 로 준 것
  │  └─────────────────────┘              │
  │  그 밖: 제품 메타데이터, 연산자 상태,  │
  │         중간 밴드, GC 여유분           │
  └───────────────────────────────────────┘
  ＋ 네이티브 (JVM 밖)
     GeoTIFF/BigTIFF 쓰기 버퍼, JAI, GDAL, HDF, 스레드 스택
```

### 이 장비의 설정

`C:\Program Files\snap\bin\gpt.vmoptions`

```
-Xmx22G
```

**한 건만 돌릴 때는 합리적인 값이다.** 31.7 GB에서 22 GB를 쓰게 해 준다.
문제는 **이 파일이 전역**이라는 것 — `gpt.exe`를 4개 띄우면 **각각** 22 GB까지
자라도 된다고 믿는다. 합쳐서 88 GB다.

### `-c`가 막아 주지 않는 이유

`-c`는 타일 캐시만 제한한다. 캐시가 5 GB로 묶여 있어도 힙의 나머지는 `-Xmx`까지
자유롭게 자란다. 게다가 **`-Xmx`가 크면 JVM은 GC를 서두르지 않는다** — 상한이
멀리 있으니 회수보다 확보가 싸다고 판단하고 계속 OS에 요청한다.

> **`-c`를 아무리 줄여도 `-Xmx`가 크면 동시 실행은 안전해지지 않는다.**

### 내가 한 잘못된 계산

```
8G + 5G + 5G + 5G = 23 GB  <  31.7 GB   →  "안전"
```

캐시만 더했다. 힙의 나머지도, 네이티브도, OS 몫도 안 뺐다.

## 4. 왜 "멈춘 것처럼" 보였나 — GC 스래싱

물리 메모리가 바닥나면 Windows가 JVM 힙 일부를 페이지 파일로 내린다.
그런데 **GC는 살아 있는 객체를 찾으려 힙 전체를 훑어야 한다.**

```
  GC 시작 → 페이징된 영역 접근 → 페이지 폴트 → 디스크에서 읽음
         → 자리 만들려고 다른 페이지를 밀어냄 → 그것도 곧 필요해짐
         → 다시 폴트 …
```

CPU는 100%로 돌지만 **실제 처리량은 0**이다. 이번 사례의 수치:

| | 14:28 | 14:43 | 해석 |
|---|---|---|---|
| CPU 누적 | 49분 | **73.2분** | 24분을 더 태웠다 |
| 산출 파일 | 1,001 MB | 1,071 MB (14:33 이후 정지) | 10분간 진전 0 |
| 프로세스 메모리 | 6,733 MB | **13,953 MB** | GC가 회수를 못 해 계속 요청 |

**메모리가 계속 늘면서 출력이 멈춰 있으면 스래싱이다.** 행 걸림(deadlock)이나
느린 연산과는 이 조합으로 구별된다.

## 5. 진단법

### 5-1. 프로세스 상태 가르기

```powershell
Get-CimInstance Win32_Process -Filter "Name='gpt.exe'" |
  Select-Object ProcessId,
    @{n='MB';e={[math]::Round($_.WorkingSetSize/1MB)}},
    @{n='시작';e={$_.CreationDate.ToString('HH:mm')}},
    @{n='CPU분';e={[math]::Round($_.UserModeTime/600000000,1)}}

Get-CimInstance Win32_OperatingSystem |
  Select-Object @{n='여유GB';e={[math]::Round($_.FreePhysicalMemory/1MB,1)}}
```

| 증상 | CPU | 메모리 | 출력 파일 | 판정 |
|---|---|---|---|---|
| 정상 | 오름 | 평평 | 커짐 | 그냥 오래 걸리는 중 |
| **스래싱** | **오름** | **계속 오름** | **정지** | 동시 실행을 줄일 것 |
| 걸림 | **멈춤** | 평평 | 정지 | 다른 원인 (I/O 대기 등) |
| 사망 | 프로세스 없음 | — | 정지 | 재실행 필요 |

**여유 메모리 2 GB 미만이면 이미 위험 구간이다.**

### 5-2. 산출물이 잘렸는지 가르기

⚠ **파일 크기나 "열리는지"로는 못 가른다.** GDAL은 안 쓰인 타일을 nodata로
채워 돌려주므로 잘린 파일도 멀쩡히 열리고 통계도 나온다.

**행 방향 유효화소 분포**로 본다. 지형보정된 스와스는 기울어져 있어 위아래로
서서히 줄어든다. 잘린 파일은 어느 행에서 뚝 끊긴다.

```
6D9F  19,113x5,679   위 |         ███▇▆▆▅▄▃▂▁| 아래   ← 정상: 마지막 행까지 닿는다
93DD  10,105x2,749   위 |▁▁▂▃▄▄▅▆▇▇█         | 아래   ← 절단: 가장 짙은 데서 끊겼다
```

93DD는 **아래로 갈수록 늘다가 최대치에서 멈췄다.** 정상이라면 거기서부터
줄어들어야 한다.

스크립트: `_row_profile.py` (scratchpad). 요지는 20개 띠로 나눠 각 띠의
`isfinite & != 0` 비율을 재는 것이다. 쓰는 중인 파일은 최근 수정 시각으로
걸러야 한다 — 미완성 타일을 읽으면 `TIFFReadEncodedTile() failed`가 난다.

## 6. 안전한 동시 실행 수

```
쓸 수 있는 메모리 = 물리 − OS·기타 (약 4 GB)
건당 상한        = 쓸 수 있는 메모리 ÷ 동시 실행 수
-Xmx             = 건당 상한보다 작게
-c               = -Xmx 의 60~70 %
```

이 장비(31.7 GB, 가용 약 27.7 GB) 기준:

| 동시 | 건당 | `-Xmx` | `-c` | 비고 |
|---:|---:|---|---|---|
| 1 | 27.7 GB | 22G | 14G | 지금 vmoptions 그대로 |
| **2** | 13.8 GB | **12G** | **8G** | **권장** |
| 3 | 9.2 GB | 8G | 5G | 큰 granule은 위험 |
| 4 | 6.9 GB | 6G | 4G | 전 granule(944M 화소)은 불가 |

### 힙을 프로세스별로 주는 법

`graph.run(gpt_options=[...])`은 `[gpt.exe, *gpt_options, graph.xml]`로
`subprocess.Popen`을 호출한다(`snapista/graph.py:476`). 따라서 gpt가 받는
옵션은 무엇이든 넣을 수 있다.

```python
graph.run(gpt_options=["-J-Xmx12G", "-q", "8", "-c", "8G"])
```

`gpt.exe -J-Xmx2G -h`가 옵션을 거부하지 않는 것은 확인했다. 다만 **부하 상태에서
실제로 힙이 제한되는지는 아직 검증하지 않았다.** 확실한 방법은 둘이다.

1. `gpt.vmoptions`의 `-Xmx`를 동시 실행 수에 맞춰 낮춘다 (전역이라 모든 실행에 적용)
2. **동시 실행 수를 애초에 2로 묶는다** ← 가장 확실하다

## 7. 근본 해법은 캐시 조정이 아니다

메모리를 쥐어짜는 것보다 **일 자체를 줄이는 게 낫다.**
`rtc_basin_extdem.py`의 자를 창을 좁히면 건당 부담이 3배 줄어든다.

| 처리 범위 | 화소 | 상대 |
|---|---:|---:|
| 전 granule | 944M | 1.00 |
| 옛 자를 창 (= DEM 창, 1.86°) | 661M | 0.70 |
| **새 자를 창 (AOI + 0.15°)** | **320M** | **0.34** |

전 granule을 4건 동시 실행하려던 것이, 자른 뒤에는 같은 메모리로 여유 있게 돈다.

> 관련: [`rtc_basin_extdem.py`](../../s1/tools/preprocess/rtc_basin_extdem.py) 모듈 주석 — `Subset`이 레이더
> 기하에서 자르는 탓에 산출 경계상자가 준 창보다 커지는 문제도 같이 정리돼 있다.

## 8. 체크리스트

작업을 걸기 전에:

- [ ] `Get-CimInstance Win32_Process -Filter "Name='gpt.exe'"` — 이미 도는 게 있나
- [ ] 여유 메모리 확인 — 걸고 나서 2 GB 아래로 갈 것 같으면 걸지 않는다
- [ ] 동시 실행 수 × 건당 상한 ≤ 물리 − 4 GB 인가
- [ ] `-c`만 보지 말고 **`gpt.vmoptions`의 `-Xmx`** 를 확인했나
- [ ] 이 granule을 이미 다른 작업이 처리하고 있지 않나
- [ ] 처리 범위를 더 줄일 수는 없나 (clip)

작업 중:

- [ ] 메모리는 오르는데 출력 파일이 멈춰 있으면 → 스래싱, 동시 실행을 줄인다
- [ ] 프로세스가 사라졌으면 → 산출물을 **행 프로파일로** 검사한다. 크기만 보면 속는다
