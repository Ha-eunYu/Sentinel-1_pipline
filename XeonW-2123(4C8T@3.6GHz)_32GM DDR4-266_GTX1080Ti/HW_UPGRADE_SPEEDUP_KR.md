## 2. 실측 전처리 속도 (2026-07-27)

모두 이 머신 단독 실행(다른 무거운 작업 없음), SNAP `gpt -q 8 -c 14G`.

| 처리 | 도구/설정 | 씬당 시간 | 처리량 | 비고 |
| --- | --- | --- | --- | --- |
| GRD RTC 10m 풀씬 | SNAP(Frost, 10m) | **~28–35분** | 0.26 Mpx/s | 754B 벤치 27.9분(440M px) |
| GRD RTC 30m | sarsen(gamma_bilinear) | 16.4분 | 0.07 Mpx/s | 출력 70M px(30m). 풀씬은 OOM |
| GRD RTC 10m 짧은씬 | SNAP(auto DEM, 부분) | 3.9분 | — | DEM 부분커버(무효) 참고치 |
| 로컬 Frost 후처리 | filtering(5×5) | ~56초 | — | 69.5M px |
| SLC RTC | SNAP | **~45–88분** | — | GRD보다 무거움(디버스트 등) |

- **씬당 시간은 출력 픽셀수(=해상도)와 코어 수에 비례**한다. 10m 풀씬(≈4.4억 화소)을
  8스레드로 처리해 ~30분이 나온다. IW GRD 스와스는 씬마다 크기가 비슷해, 파일 용량
  보다 해상도가 시간을 지배한다.
- **한 캠페인 배치**(예: GRD 17 + SLC 14 = 31씬)는 순차 처리로 **하루(~20시간 이상)**
  걸린다(RAM_증설_요청_근거.md §3과 일치).

## 3. 속도 한계의 근본 원인 (자원별)

### 3.1 CPU — 씬당 속도의 실질 상한

- SNAP `gpt`는 타일을 **멀티스레드**로 처리한다. 처리량(0.26 Mpx/s)은 **8스레드
  (4물리코어)** 를 이미 꽉 채운 값이다. `-q`를 8보다 키워도 물리코어가 4개뿐이라
  더 빨라지지 않는다.
- 즉 **씬당 시간을 줄이려면 물리코어를 늘리는 수밖에 없다.** RAM을 아무리 늘려도
  씬 1장의 처리 시간(30분)은 그대로다.

### 3.2 RAM — 병렬·캐시·sarsen 풀씬의 제약

- **씬 병렬 불가**: SNAP 씬 1개가 Working Set **14–18GB**(캐시 `-c 14G` 포함)를
  쓴다. 32GB에선 2개를 동시에 못 돌린다(OS 여유 3–5GB로 붕괴). → 순차 강제.
- **타일 캐시 제한**: RAM 부족으로 `-c`를 14G로 묶어, 캐시를 넘는 데이터는 HDD에서
  반복 재읽기 → 씬당 속도 손해.
- **sarsen 풀씬 OOM**: SNAP-free(sarsen) 경로는 full float64 그리드를 적재해 풀씬
  지오코딩에서 피크 ~22GB+ → 32GB(여유 ~22GB)에서 `MemoryError`. 짧은 씬만 되고,
  `--tc-chunks 256`으로 겨우 회피하나 느리다([RTC_BENCHMARK_KR.md](RTC_BENCHMARK_KR.md) §3.2).

### 3.3 GPU — 현 파이프라인 미사용

- **SNAP `gpt`의 RTC 연산자**(Calibration·Terrain-Flattening·Range-Doppler
  Terrain-Correction 등)는 **CPU(JAI 타일) 전용**이다. GPU를 쓰지 않는다.
- **sarsen**도 numpy/scipy/dask 기반 **CPU 연산**이다(cupy 등 GPU 백엔드 미사용).
- 따라서 **현재 RTC 워크플로에서 GTX 1080 Ti는 놀고 있다** — GPU 증설/교체는
  RTC 속도에 **직접 효과가 없다**. (예외는 §4.3.)

### 3.4 저장장치 — 부차적

- 입력 zip은 처리 전 **C: SSD 임시폴더로 복사**되고, DEM 캐시도 C: SSD에 있어
  **읽기는 SSD**다. 출력 BigTIFF만 F: HDD에 쓴다(기존과 동일). 디스크는 현재
  주 병목이 아니다(HDD 출력 쓰기는 전체의 소수 %).

## 4. 증설별 기대 단축 효과 (정량 추정)

> 추정 전제: SNAP RTC의 **CPU 연산 시간은 물리코어 수에 거의 선형**으로 스케일
> (타일 병렬), 씬당 I/O·기동 오버헤드는 코어 수와 무관한 상수(~2–4분)로 둔다.
> 실제 값은 씬·클럭·메모리대역폭에 따라 ±20% 편차.

### 4.1 RAM 증설 (32GB → 64 / 128GB)

RAM은 **씬당 시간을 거의 줄이지 못한다**(CPU-bound). 대신 세 가지를 푼다:

| 효과 | 32GB(현재) | 64GB | 128GB |
| --- | --- | --- | --- |
| 동시 씬 수(메모리 한계) | 1 | 2–3 | 4–6 |
| 실효 병렬(4물리코어 한계) | 1 | **~1.3–1.6×**\* | ~1.5–1.8×\* |
| SNAP 타일캐시 `-c` | 14G | 28–40G | 48–96G |
| sarsen 풀씬 RTC | ✗ OOM | **✓ 기본 청크 OK** | ✓ 여유 |
| SLC(무거움) 안정성 | 빠듯 | 안정 | 안정 |

\* **주의**: 씬 2개를 병렬로 돌려도 물리코어가 4개뿐이라 각 씬이 코어를 나눠 써
**2배가 아니라 ~1.3–1.6배** 배치 처리량만 는다(메모리대역폭·캐시 경쟁 포함). RAM
단독 증설의 배치 단축은 **부분적**이다. 다만 **sarsen 풀씬 가능·캐시 확대·SLC 안정성**
이라는 질적 이득이 크다.

- 배치(31씬, 현재 ~20h) → **64GB: ~13–16h**(부분 병렬+캐시), 128GB: ~12–15h.

#### 4.1.1 Dell 확인 메모리 스펙 (구매 시 — Case (생략) / Service Tag (생략))

Dell 기술지원(2026-07-15, Kangsan Kim 회신, 연락처 080-854-0066)으로 이 워크스테이션
(Service Tag **(생략)**)의 호환 메모리를 확정했다:

- **Xeon W CPU 장착 → ECC Registered DIMM(RDIMM) 필수.** 일반 UDIMM은 장착 불가.
  기존 16GB 모듈도 ECC로 확인됨.
- **부품번호(정정)**: `HMAA8GR7AJR4N-XN` = **64GB** DDR4-3200 ECC RDIMM(이전 "16GB"는
  오류). Dell이 실제 확인한 부품은 **`HMA84GR7CJR4N-WM` = 32GB** DDR4-2933 ECC RDIMM 2R.
- 증설 구성(6슬롯 여유, 기존 모듈 유지):
  - **32 → 64GB(권장)**: **16GB RDIMM 2개 추가 → 16GB×4** (4채널 모두 사용=대역폭↑).
    현재 16GB 부품번호는 `Get-CimInstance Win32_PhysicalMemory`로 확인 후 동일/호환 구매.
  - **32 → 128GB(장기)**: **HMA84GR7CJR4N-WM 32GB × 4** (4채널, 1 DIMM/채널).
  - 2933/3200 모듈도 W-2123에선 **2666으로 다운클럭(정상)**.
  - **64GB 단일 DIMM은 Skylake-W(W-2123) 지원을 Dell에 재확인 후 구매**(64GB DIMM은
    주로 Cascade Lake-W 구성).

### 4.2 CPU 증설 (코어 수 ↑) — 씬당 속도의 핵심 지렛대

SNAP은 코어에 **완전 선형이 아니다**(병렬화 안 되는 연산·메모리대역폭·타일 캐시·DEM
접근·GeoTIFF 출력이 섞임). 따라서 **보수적 처리량 개선 범위**로 본다(기준: 실측 평균
~41분/씬, 배치 31씬 ~21h):

| CPU 변경 | 처리량 개선(보수적) | 씬당(평균) | 배치 31씬 |
| --- | --- | --- | --- |
| 4 → 8코어 (W-2145 등) | 약 1.5–1.9× | ~22–27분 | ~11–14h |
| 4 → 10–14코어 (W-2155/2175) | 약 2–3× | ~14–20분 | ~7–10h |
| 4 → 18코어 (**W-2295**) | 약 2.5–4× | ~10–16분 | ~5–8h |

정확한 값은 **동일 씬·그래프·해상도 A/B 벤치마크**로만 확정 가능. 위는 상한이 아닌
예상 범위다. **CPU 교체 전 PSU(950W)·히트싱크(165W)·BIOS/ST 호환 확인 필수**(§본체 주의).

- **씬당 시간을 실제로 줄이는 건 CPU 코어**다. 4→16코어면 씬당 ~1/3.
- 단 코어를 늘리면 **각 씬이 더 많은 스레드를 쓰므로 메모리도 더 필요**하다
  (`-c` 캐시·중간버퍼). 그래서 **CPU 증설은 RAM 증설과 함께** 해야 효과가 온전하다
  (코어만 늘리고 RAM 32GB면 캐시·병렬이 다시 발목).

### 4.3 GPU 증설 — 현 RTC엔 효과 없음, 특정 확장에만

- **SNAP·sarsen RTC는 GPU를 안 쓴다** → GPU 교체(예: 1080 Ti → 4090)로 **RTC
  속도는 그대로**다. 현 워크플로 기준 **비용 대비 효과 0**.
- GPU가 의미 있는 경우(현재 아님, 도입 시):
  - **딥러닝 수체/홍수 탐지**(U-Net 등)로 임계값 방식(Otsu)을 대체·보강할 때 학습·
    추론 가속.
  - GPU 가속 라이브러리 재구축(cupy/RAPIDS, GPU-GDAL) — sarsen류를 GPU로 포팅하는
    별도 개발이 필요(현 코드로는 이득 없음).
  - 대량 영상 시각화·재투영(일부 GPU 경로) — 부차적.
- 결론: **RTC 처리 속도만 놓고 보면 GPU는 후순위**. 탐지 알고리즘을 딥러닝으로
  확장할 계획이 생기면 그때 1080 Ti(11GB)로도 시작 가능, 대형 모델은 24GB급 고려.

## 5. 우선순위 권고 (비용 대비 효과)

| 순위 | 조치 | 무엇이 빨라지나 | 근거 |
| --- | --- | --- | --- |
| **1** | **RAM 64GB(→128GB)** | sarsen 풀씬 가능, 캐시 확대, 4채널 대역폭, SLC·스왑방지 안정 | 6슬롯 여유 → 추가 장착. 64GB=16GB×4, 128GB=32GB×4(Dell 확인 HMA84GR7CJR4N-WM), §4.1.1 |
| **2** | **CPU 16코어급** (+RAM 동반) | **씬당 시간 ~1/3**, 배치 ~1/3 | 씬당 속도의 유일한 지렛대 |
| 3 | 출력도 SSD | 씬당 소폭(출력 쓰기) | HDD→SSD 여유 시 |
| — | GPU 교체 | RTC엔 **효과 없음** | SNAP/sarsen CPU 전용 |

**요약**:

- **당장·저비용**: RAM 64GB 증설(기존 모듈 유지, 6슬롯 여유). sarsen 풀씬을 열고
  SNAP 캐시·SLC를 안정화하며 부분 병렬로 배치를 ~20h→~14h로.
- **씬당 속도까지**: **CPU 코어 증설(16코어급)+RAM 동반**이 근본 해법. 씬당
  30분→~10분, 배치 ~20h→~6–7h.
- **GPU**: 현 RTC 파이프라인엔 무의미. 딥러닝 탐지로 확장할 때만 재검토.

## 6. 부록 — 측정 근거

- SNAP GRD RTC 10m 754B: `PROCESS_SECONDS` 1674s(27.9분), 출력 32183×13678(440M px),
  0.26 Mpx/s ([RTC_BENCHMARK_KR.md](RTC_BENCHMARK_KR.md) §3).
- sarsen 754B: 984s(16.4분), 70M px(30m), 0.07 Mpx/s. 풀씬은 지오코딩 interp에서
  ~22GB+ 피크로 `numpy MemoryError`(§3.2).
- 씬 1개 SNAP Working Set 14–18GB, 처리 중 여유 RAM 3–5GB (RAM_증설_요청_근거.md §2).
- CPU/스레드: `Win32_Processor` 실측 4코어/8스레드. GPU: `Win32_VideoController`
  GTX 1080 Ti. RAM: DDR4-2666 16GB×2, 8슬롯 중 2슬롯.
